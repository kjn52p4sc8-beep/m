# ローカル保存を維持するクラウド同期設計

2026-10-31。設計のみで、同期・ログインが利用できるUIは追加していません。既存のDexie、UUID、JSONバックアップを残します。新しい契約・プロジェクト作成・メモの外部送信は行っていません。

## 候補・費用・設定

Supabase Auth / Postgres / Storage / RealtimeとNetlify Functionsを候補とします。料金は認証利用者数、DB・画像・音声容量、帯域、Realtime接続、関数実行量で変わります。公式の [Supabase料金](https://supabase.com/pricing) と [Netlify料金](https://www.netlify.com/pricing/) を契約時に確認します。この環境では最新料金を取得できないため、無料枠や月額を保証しません。利用人数・容量・月額上限を決め、超過前の通知・停止方針を合意してから導入します。

設定には専用ステージング環境、Authの公開URL／リダイレクトURL、メール送信設定、Google/Appleを使う場合のプロバイダー登録、秘密鍵のサーバー環境変数が必要です。service_roleやOAuth秘密鍵はVITE_*変数へ入れません。公開可能な接続情報にも必ずサーバー側のアクセス制御を併用します。

## 所有者・アクセス制御

- `notes(owner_id, local_id, revision, payload, deleted_at, updated_at)`：主キーはowner_id + local_id。既存ノートのUUIDを変えません。payloadに既存の色・リンク・チェック項目・リマインダー等を保持。
- `attachments(owner_id, local_id, note_id, sha256, storage_path)`：バイナリは非公開Storageへ。パスはowner/note/attachment。期限付きURLは認証と所有権確認後だけ発行。
- `migration_runs(owner_id, device_id, run_id, local_manifest, completed_at)`：移行の再開・照合記録。
- 通常メモは非公開。RLSで `auth.uid() = owner_id` をSELECT/INSERT/UPDATE/DELETEすべてに適用。共有を後日追加するときはmembershipsに閲覧・編集・管理の権限を定義し、別の検証済みポリシーを追加します。
- 他ユーザーのID指定、所有者の書き換え、Storage直アクセス、ログアウト済みトークンを使った操作を拒否するテストを必須とします。

## オフライン・競合

ローカルDBの保存を先に完了し、同じトランザクションでoutboxに操作UUID・対象ID・基準revisionを記録します。認証した所有者ごとにキューを分離します。再送は操作UUIDで冪等に処理します。

更新は `WHERE revision = expected_revision` の条件付きで受理し、revisionを増加。競合時はローカル版・サーバー版・共通基準を残し、利用者が比較して選択します。単純な後勝ち上書きは行いません。Realtimeは変更検知に限定し、永続化・再接続時の差分取得を省略しません。削除もtombstoneとして同期し、復元可能期間中は添付を削除しません。

## 既存メモの移行・復旧

1. ログイン前にJSONを書き出し、対象メモと添付の件数・ハッシュを端末内で記録。
2. ログイン後に送信先アカウントと対象範囲を確認して、利用者が移行を開始。自動アップロードしない。
3. owner_id + local_idの一意制約で重複を防ぎ、添付はハッシュで照合。途中中断から再開可能にする。
4. サーバーの件数・内容・添付ハッシュが一致した対象だけを移行済みにする。移行が成功しても元のローカルデータを削除しない。
5. 失敗時はローカル保存を継続。サーバー側の未完了分はrun_idで追跡し、他のデータを巻き込まず整理可能にする。
6. ログアウトでローカルデータを削除しない。別アカウントには無断で再送せず、所有者ごとの領域・同意を維持。

必要な受け入れテスト：旧DBからの移行、途中切断と再試行、別端末の同時編集、オフライン削除と復元、複数アカウント切替、巨大添付、権限の否定ケース、JSONからの復旧。クラウド基盤がないため、これらのクラウド試験はまだ実行していません。
